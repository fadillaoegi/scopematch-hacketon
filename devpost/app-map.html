From a sealed answer
to a shared scope.

A freelancer and client answer separately, compare what they imagined, settle each decision, and confirm one saved scope. React draws the screens. Go enforces the rules. SQLite keeps the records through a repository interface; the use cases do not depend on the database adapter.

This is a reference route for the completed proof of concept. The learning wrap-up used a brief evidence-based recap; no interactive code tour is claimed. The map is an offline snapshot; refresh it after changes to the mapped behavior.

02 · Rule + SQLite

Validate, then seal

scope/answers.go → Submit()

Every selected question must be answered. A repository transaction stores the submission; later edits are rejected. SQLite implements that application-owned port.

→
03 · Visible result

Wait, or reveal together

scope/session.go → buildSession()

Other-party answers are omitted until both submit. The response then unlocks Compare.

  1. Frontend: scopematch_FE/src/components/AnswerFlow.tsx — search async function submit. The component saves answers, sends the submit request, and renders the sealed waiting state. src/application/projectGateway.ts defines the port; src/main.tsx injects the HTTP adapter, which adds the link token.
  2. Domain rule: scopematch_BE/internal/scope/answers.go — search func (s *Service) Submit. Rule checks and the submission write share one transaction through scope.Repository; store.NewRepository implements it using SQLite. Matching concrete answers get a system proposal, with no automatic confirmations.
  3. Response boundary: scopematch_BE/internal/scope/session.go — search func buildSession. Own answers are returned; other answers are queried and included only after both submit. CompareBoard.tsx displays the allowed response with the two ink colors.

Clean Architecture is required for future changes. See AGENTS.md and architecture boundaries. The backend application depends on its own repository port, and the frontend presentation consumes an injected gateway.

Proposal replacement

scope/resolve.go → Propose() deactivates the old proposal. The new one starts with only its proposer's confirmation.

Versioned agreement and export

scope/versions.go → ConfirmVersion() checks the latest saved version and active decisions. scope/export.go → Export() reads the stored agreed snapshot.

A practice to reuse

Turn a requirement into an observable check at the boundary that controls it. “Answers stay private” becomes “the raw session JSON has no other.answers before both submit.”

TestAnswersStaySealedUntilBothSubmit checks that absence directly, including secret custom-answer text. TestUndecidedOrReplacedDecisionsCannotBeAgreed applies the same approach to a stale scope. A hidden UI element alone would not establish either rule.

For another project, choose the user-visible guarantee first, identify the code that must enforce it, then test the response or stored result a second user could actually observe.

Run it again

From the repository root, use two terminals. Requirements and the complete salon demo are in README.md.

cd scopematch_BE

cd scopematch_FE
npm ci

cd ../scopematch_BE
go run ./cmd/server -static ../scopematch_FE/dist -seed-demo
Where state lives and how to check the rules

SQLite in scopematch_BE/data/ stores projects, answers, proposals, versions, and confirmations. Browser local storage remembers owner links and whether the reveal has played. There are no external runtime services or API keys.

cd scopematch_BE
go test ./...
go vet ./...

The frontend check is npm run build from scopematch_FE.
